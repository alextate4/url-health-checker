<objective>
Add the over-time view. The API returns each URL's check results for a chosen window (HIST-03).
The dashboard gets a 1h/24h/7d picker, uptime % and average response time over the window, a
colored strip of recent checks, and refreshes every 5 seconds without a page reload
(DASH-03..DASH-06). This covers ROADMAP Phase 2 success criteria 1–4.

**Design (log it as D-018 in Task 3):** a 7d window holds about 20,000 checks for each 30s URL,
so the browser never gets every check on each poll.
- `GET /api/urls?window=1h|24h|7d` (no window means 1h; any other value returns 400). It returns
  the Phase 1 shape (D1-12) plus `summary: { checkCount, uptimePercent, avgResponseTimeMs, recent }`.
  `recent` is at most the 30 newest checks inside the window, oldest first. It is one request per
  poll, and its size does not depend on the window.
- For each URL, two small SQL queries work out the summary: one aggregate (COUNT/AVG) and one
  `ORDER BY checked_at DESC LIMIT 30`. Both use the existing `(url_id, checked_at)` index (D1-07).
  The orchestrator's steer suggested one `GROUP BY` for all URLs. This plan uses one query per URL
  instead: the strip needs a per-URL `LIMIT` query anyway, and this way C# has no rows to merge by
  `url_id`. SQLite runs inside our process, so a small query costs microseconds, not a network
  round trip.
- `GET /api/urls/{id}/checks?window=…` returns every check of one URL inside the window (HIST-03).
  It is not polled.
- The cutoff is `DateTime.UtcNow - window`, passed to SQL as `"o"` text and compared with
  `checked_at >= @Since` (D1-08).
- `avgResponseTimeMs` counts only checks that got an HTTP response (log it as D-019 in Task 3). A
  DNS failure "answers" in about 2 ms and a timeout in 10,000 ms. Neither is a response time.
  Uptime % already shows those failures.

Order (tracer-first): Task 1 builds the thinnest full path: the window whitelist, the SQL
aggregate, the dashboard JSON, the picker, the uptime/avg columns, and polling. Task 2 adds the
recent-checks strip and the per-URL history endpoint. Both reuse Task 1's window path. Task 3
writes the decisions, edge cases, AI notes, and concept notes.

Output: a dashboard that shows behavior over time, and a story-telling commit history.
</objective>

**Aggregate (per D-018 and D-019).** Add `GetWindowSummaryAsync(long urlId, DateTime since)`. Run
one query on `check_results WHERE url_id = @UrlId AND checked_at >= @Since`. Select `COUNT(*)` as
CheckCount and `ROUND(AVG(healthy) * 100, 1)` as UptimePercent. `healthy` is 1 or 0, so its

AVG skips NULL, so only checks that got an HTTP response count (D-019). With zero matching rows,
SQLite returns 0 and NULL, NULL. That gives JSON nulls with no extra code. At planning time this
SQL was run against a copy of the DB: the unreachable seed gave 0.0 and NULL, and an empty window
gave 0, NULL, NULL. Dapper fills a small private settable class (for example `StatsRow`). Do not
fill the positional record directly. Phase 1 hit the SQLite Int64 mapping problem and used flat
row classes for this reason (see `StatusRow`).

**Cutoff as text (D1-08). This is the main pitfall.** Pass `@Since` as `since.ToString("o")`, a
string. Do not pass a `DateTime` object. Microsoft.Data.Sqlite writes a DateTime parameter as
`yyyy-MM-dd HH:mm:ss.FFFFFFF` (a space, no `Z`). Compared as text with our `…T…Z` rows, that
would let older rows from the same day into the 1h window. The verify probe catches this. Callers
must build `since` from `DateTime.UtcNow` (not `DateTime.Now`), so the `"o"` text ends in `Z`,
like the stored rows.

**Dashboard read.** Add `GetDashboardAsync(DateTime since)`. It calls `GetUrlStatusesAsync()`,
